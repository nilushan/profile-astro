## Project Overview

This was a coordinated improvement to a production Google Cloud Platform environment rather than a single isolated optimisation. It addressed four related concerns:

1. Continuous Cloud SQL storage growth from time-series data
2. Cloud Logging volume and cost
3. Consistency of deployments across development, staging, and production
4. Long-lived credentials in CI/CD and service workloads

The result was a platform with controlled storage and logging cost growth, a predictable data-retention process, repeatable multi-environment delivery, and keyless access to GCP resources.

## The Challenge

Time-series systems naturally accumulate data. Keeping all historical records in the active Cloud SQL database increased storage usage and therefore recurring cloud cost. Large row-by-row deletion jobs were also an inefficient way to enforce retention and could add avoidable database load.

At the same time, application logs included messages with limited operational value, increasing Cloud Logging ingestion and storage. Deployment definitions had to support multiple services and environments without allowing copies of Kubernetes manifests to drift. CI/CD and deployed services also needed a safer alternative to long-lived service-account key files.

## Cloud SQL Time-Series Partitioning

### Monthly range partitions

I organised time-series data in Cloud SQL for PostgreSQL using monthly range partitions. Time-bounded queries for recent records can use PostgreSQL partition pruning so the database only examines the relevant partitions rather than the entire historical dataset.

The monthly boundary provides a practical operational unit: it is fine-grained enough for common recent-data queries while being large enough to keep partition management straightforward.

### Archive, then drop

Once a partition passes its active retention period, it can be archived outside the operational database and then dropped. Dropping an old partition is substantially simpler and faster than issuing a large row-by-row `DELETE`, and it avoids retaining expired data in active Cloud SQL storage.

This created a repeatable lifecycle:

1. Create upcoming monthly partitions before they are needed
2. Route new time-series records into the correct partition
3. Query recent windows using partition pruning
4. Archive partitions that have passed the active retention period
5. Validate the archive and drop the old partitions
6. Monitor storage growth and repeat on a schedule

### Cost and performance impact

Controlling the active dataset constrained Cloud SQL storage and its associated cost growth over time. The same design improved access to recent time-series data because queries can avoid scanning irrelevant historical partitions.

## Logging Optimisation

I reviewed application logging with the goal of preserving useful operational signals rather than simply logging less. Essential context for monitoring, troubleshooting, and auditability remains available, while repetitive or low-value messages are no longer sent to Cloud Logging (formerly Stackdriver Logging).

This reduced ingestion and retention volume while keeping logs actionable for production support.

## Build Once, Deploy Many

The CI/CD flow was standardised around immutable artifact promotion:

1. A main-branch build creates a versioned container image
2. The image is published to a shared Artifact Registry
3. Development, staging, and production deploy that same artifact
4. Runtime-specific deployment steps target Kubernetes, Cloud Run, or Firebase as required

Building once and promoting the result means each environment runs the artifact that was already tested. It reduces environment drift and avoids subtle differences caused by rebuilding the same commit separately for each environment.

## Reusable Kubernetes Configuration with Kustomize

Kubernetes manifests were restructured with Kustomize:

- A **base** contains common resources and configuration
- **Service overlays** contain service-specific changes
- **Environment overlays** contain development, staging, or production differences
- CI renders the selected composition into standard Kubernetes manifests before deployment

This keeps shared definitions in one place while making every intentional difference explicit and reviewable. It also avoids maintaining nearly identical manifest copies for every service/environment combination.

## Keyless GitHub Authentication

GitHub Actions now authenticates to GCP through Workload Identity Federation. Rather than storing a long-lived service-account JSON key in GitHub secrets, the workflow exchanges its GitHub OIDC identity for short-lived GCP credentials.

Those credentials allow the workflow to perform only its authorised operations, including publishing to Artifact Registry and deploying to the target environment. This reduces secret rotation overhead and removes a high-value static credential from CI/CD.

## Keyless Workload Access in GKE

Service workloads were also moved away from mounted service-account key files. With Workload Identity Federation for GKE, Kubernetes service accounts are associated with authorised GCP identities, allowing workloads to obtain short-lived credentials at runtime.

Each workload can use a dedicated service identity and least-privilege IAM roles for the GCP resources it needs. The application no longer needs to know where a JSON key is mounted, and there is no long-lived private key to distribute among pods.

Artifact access and workload-to-GCP access now fit the same overall model: use platform identity and short-lived credentials instead of copied keys.

## Results

### Cost control

- Constrained recurring storage-related cost growth
- Kept active Cloud SQL storage low through scheduled archival and partition removal
- Reduced Cloud Logging volume by eliminating low-value messages
- Made future storage growth more predictable

### Performance and operations

- Improved recent time-series query paths through partition pruning
- Made historical-data removal a fast partition lifecycle operation
- Created an explicit archive-before-delete process
- Preserved essential logs for production troubleshooting

### Delivery consistency

- Established a shared Artifact Registry as the source for environment deployments
- Promoted the same versioned build through development, staging, and production
- Supported Kubernetes, Cloud Run, and Firebase deployment paths
- Reduced duplicated Kubernetes YAML through composable Kustomize bases and overlays

### Security

- Replaced static GitHub-to-GCP credentials with short-lived federated access
- Removed mounted service-account key files from workloads
- Enabled service-specific, least-privilege identities in GKE
- Reduced secret distribution, storage, and rotation responsibilities

## Next Steps

The platform can be improved further by automating partition creation and archive validation, defining retention objectives as policy, tracking storage and logging cost trends on dashboards, and attaching approved before/after metrics to each optimisation.
